## 이 저장소 자체의 임의 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 병렬 부스터 구간 Δv 계산 방식 | REQUIREMENTS.md 4절의 "유효 Isp" 근사법 사용 | 인수 문서가 "03_physics.md 6.3절 질량 표를 따른다"고 했으나 해당 문서를 아직 전달받지 못해 표준적인 근사식으로 구현. 원본 문서 입수 시 재검토 |
| 코드 실행 확인 방법 | `npx serve` 또는 `python -m http.server` 등 정적 서버로 `index.html` 확인 | ES 모듈은 `file://`에서 CORS로 막히므로 |
| 테스트 실행 방법 | Node.js로 `node tests/*.test.js` 직접 실행 (별도 테스트 프레임워크 미사용) | 의존성 없이 바로 검증 가능하게 하기 위함 |

| 테스트 실행 환경 | Node.js가 로컬에 설치되어 있지 않아, `tests/*.test.js`는 아직 Node로 직접 실행해 확인하지 못했다. 대신 `tests/browser-check.html`을 정적 서버로 열어 동일한 로직(같은 `src/` 모듈)을 브라우저에서 검증했고 전체 통과했다 | 개발 환경 제약. Node 설치 후 `npm test`로 재확인 권장 |
| 조립 UI 상호작용 방식 (A4) | 3D 장면에 자유롭게 드래그해 붙이는 방식 대신, 단(stage) 카드에서 부품 종류를 드롭다운으로 고르고 3D는 그 결과를 보여주는 미리보기로 구현 | 자유 3D 드래그+스냅은 구현 난이도가 훨씬 높다. 카드 방식으로도 R-01~R-06 요구사항의 실질적 기능(조립·단 편성·회수·실시간 계산)은 동일하게 충족되어 우선 이 방식으로 진행. 사용성 피드백 후 재검토 |
| 불러오기(R-08) 왕복 시 수치 보존 | `.rocket.json`을 불러오면 카탈로그에서 가장 가까운 부품(엔진/탱크)으로 매칭해 조립 상태를 재구성한다. 이 상태를 다시 내보내면 dryMassKg 등이 원본 파일의 원래 숫자와 정확히 같지 않을 수 있다 | 이 도구는 "임의의 숫자가 담긴 JSON을 그대로 보존"하는 게 아니라 "부품 조합으로 로켓을 조립"하는 도구이기 때문에 발생하는 당연한 근사. 다른 설계 도구(예: 원본 문서가 만든 파일)로 만든 파일을 불러오면 그 파일 고유의 dryMass 값 대신 우리 카탈로그 기준으로 재계산된 값이 쓰인다 |
